Every load-bearing choice, why it was made, and whether it is still open. Kept
**in the repo** rather than in the wiki on purpose: a decision is worth reviewing
in the same pull request as the change that makes it, and worth being able to
`git blame`.

The prose it used to live at the end of is in the wiki:
[Architecture](https://github.com/FullmetalBober/Indexterity/wiki/Architecture).

| D19 | **"Cannot tell" is never spelled "all clear"** | Jul 2026. Losing a cluster for days or weeks used to end badly: `$collStats`/`$indexStats` counters are cumulative since mongod started, so a restart during the observe window made `current − baseline` negative, which failed the minimum-ops check and read as *no regression* — the drop then proceeded on evidence that no longer existed, with the pre-flight's `$indexStats` check equally reset. | D23 | **The observe window scales to the index's age, not just its usage** | Jul 2026. The window already stretched for periodic usage and shrank for long-proven idleness, but both keyed on the history's *span*, which conflated two different things: how long we have watched, and how long the index has existed. A hand-made ad-hoc index — created, used once by whoever made it, forgotten — has a short span, so it got the full flat month before removal, the slowest possible treatment for the clearest possible case. Two rules added: an index that appeared while we were watching and has never been used is observed roughly as long as it has existed (≥ 7d, ≤ policy), since its entire life is on record and there is no hidden history to wait out; and an index in place ≥ 2× the policy window that saw real use gets 1.5× the policy, because whatever wanted it may want it again on a cadence longer than anything recorded. Age is only claimed when the index first appears at least a day after the cluster's earliest snapshot — collection starts at onboarding, so otherwise every index on a new cluster would look newborn and get fast-tracked, which is the warmup hazard rather than a fix for it | Locked |

| D25 | Server state through TanStack Query, **one key per api call** | Started as three keys — pipeline, telemetry, policy — rather than one blob, so approving a recommendation stops refetching the latency series. | D22 | **One auto-approval control, not two** | Jul 2026. `autoApply` (boolean) and `autoApplyScore` (threshold) read like a switch and its dial but were mutually exclusive branches, and the boolean won: setting both silently discarded the number the owner had typed directly beneath the checkbox. The boolean also promoted `ADVISORY_REVIEW` rows, which the score path explicitly excluded — and an approved advisory is worse than useless, because `classify` only deletes and re-inserts PROPOSED rows, so it leaves the refresh pool and is never re-evaluated even after the index starts being used again. `autoApply` is deleted: `autoApplyScore` alone means null = a human approves everything, 0 = everything auto-approves, 1-100 = a confidence floor, advisories never at any setting. Strictly more expressive than the pair, and both bugs stop existing rather than being fixed. Migration carries `auto_apply = true` across as threshold 0 — the behaviour that was actually running | Locked |
| D21 | **The change window picks itself when unset** | Jul 2026. An unset window used to mean "run elective changes at any hour", which is the worst default available: the one moment a drop's brief collection lock is least welcome is peak traffic, and the owners least likely to configure a window are the ones least able to absorb that. The engine now derives one from the cluster's own `latency_samples` — cumulative counters differenced, bucketed into the four 6h slots of the UTC day, quietest slot wins — and re-derives it after every collect so it tracks a workload that moves. Six hours is the honest resolution: collect runs every 6h, so claiming an hour-level window would be precision the evidence does not have. It refuses to guess rather than guessing badly: three clean observations per bucket minimum, the quiet slot must be ≤ 75% of peak (a flat day yields nothing), and intervals crossing a counter reset or a collection gap are discarded. Stored in `inferred_window_*`, apart from the owner's columns, so an explicit setting always wins and clearing it returns to auto instead of freezing the last guess | Locked |

| D17 | **Dynamic observe window** + recurrence floor | Jul 2026. The observe window is decided per drop at hide time from the index's own usage history (`analysis/observe.ts`, stored in `recommendations.observe_days`, reason in the audit trail): periodic usage extends to 2× the largest activity gap (≤ 90d) so a monthly job gets a full cycle inside the window; zero usage across ≥ 2× the baseline shortens to half (≥ 7d). Policy stays the baseline and the fallback. Workload shapes now need ≥ 3 sightings to propose and ≥ 5 for instant apply — a manually-run heavy query once or twice produces nothing. **The freeze has exactly one exception (#270)**: an owner can SHORTEN a stamped window, never lengthen it, floored at the time already served — a window shortened into the past would be due the instant it was written and "shorten" would quietly be spelled "drop now". Without it the only exit was to cancel the drop, which re-proposes it later and recomputes the identical window from the identical history; lengthening stays the policy baseline's job. It shortens the OBSERVATION and no gate: the change window and the regression check are still ahead of the drop. **Revised Aug 2026 (#263): every rule above is phrased in ACTIVITY, and for two months it was fed the COUNTER.** `$indexStats.accesses.ops` is cumulative — D19 already established that for the regression gate, and the observe path missed the same fact — so `apply.ts` summing `per_member[].ops` handed `dynamicObserveDays` a number that climbs while an index is queried and holds perfectly still while it is not. `ops > 0`, which every rule reads as "was queried during this span", was therefore true of any index used once since the member's `since`. Two consequences, both measured on the real function before the fix. An index queried once thirty days ago and an index queried every hour for thirty days produced byte-identical output — `{days: 7, "queried steadily and still in use"}` — because run-length storage collapses a flat counter into one long run whose interior gap is `span/(observations-1)`, the collect cadence, and whose `lastSeenAt` is always now. And the periodic rule was unreachable for the shape it was written for: a monthly job leaves the counter flat BETWEEN its runs, so the runs are contiguous and there is no gap left to measure. The fix is a boundary, not a rule — `usageSeries` differences consecutive readings (counting a member in full when its `since` moved, since a restarted counter is not a continuation) and splits a run that moved into the activity at the instant it jumped plus the silence that followed, which is what the span after a jump actually is. Every threshold keeps its value and every existing test its meaning; the engine was right and its input was not | Revised |

| D36 | **A trust threshold is a duration, never a count of collect intervals** | Aug 2026 (#19). The engine's usage gates were written as interval counts — `minActiveIntervals: 12`, `recentWindow: 3` — and they only meant what they appeared to mean because a collect interval happened to be six hours. Twelve intervals *was* three days of traffic and three trailing snapshots *was* the last twelve hours, at that cadence and no other. Change `0 */6 * * *` to `*/15` and the same numbers silently buy an eighth of the evidence: the engine starts calling an index dead on three hours, with no code change, no config change, and nothing failing. That is the trap, and it is the reason this landed **before** any cadence change rather than with one. `minActiveIntervals` becomes `minActiveHours: 72` and `activeIntervals()` becomes `activeHours()`; `recentWindow` becomes `recentHours: 12`. The second was not in the issue and is the more dangerous of the two: it is the line between PERIODIC_ALIVE and the **droppable** PERIODIC_DEAD, so at a fifteen-minute cadence a nightly job that had simply not run yet today would have read as decommissioned. `minHistory` deliberately stays a count — it is how many data points distinguish a pattern from a flat line, a question about samples rather than time, and `minHistoryDays` beside it is the durational half of the same gate. Two things fell out of writing it. `activeHours` credits each interval at most the series' **median gap**, taken from the data because a pure engine cannot know what the scheduler is set to: without the cap a single outage would credit its whole length as traffic the moment the counter had moved anywhere inside it, so one dark afternoon could manufacture the three days a drop needs. And the tests had to grow timestamps — a fixture where every snapshot shared one `capturedAt` could express "three snapshots" but not "went quiet", which is exactly the confusion being removed. Separately, and the part the issue identified as the real complaint: **a newly connected cluster is collected immediately**, queued from `storeCluster` and best-effort, so a failed enqueue cannot turn a connect that already committed into an error. Waiting up to six hours to see anything was what read as "the cadence is too long", and one job on connect answers it without changing steady-state load at all. The cadence itself is left at 6h on purpose — it is now *safe* to change, since none of the numbers move with it, and what remains is a cost question (how much collection load buys how much reduction in the one-interval blast radius of a mongod restart) that deserves its own decision rather than a ride on this one | Locked |

| D35 | **The unbounded tables virtualize with spacer rows, not absolute positioning** | Aug 2026. Recommendations is collections × indexes and the per-collection footprint is one row per collection; neither `listRecommendations` nor `getCollections` applies a limit, so both are unbounded in the only direction that matters — a large customer. Virtualized with TanStack Virtual behind one `virtualize` prop on `DataTable`, and three things about *how* are the decision. **Spacer rows rather than absolutely-positioned ones**, which is what the library's own table examples do: a `<tr>` taken out of the flow stops sharing the table's column widths, so the columns lose alignment the moment you scroll, and it stops being a row to a screen reader, which is most of what a `<table>` is for. Two `aria-hidden` spacers of the right height buy the same DOM saving and cost the table nothing — and because `getAllByRole` skips aria-hidden nodes, the existing order and filter tests kept working unchanged, which is the same fact from the test side. **The height is a maximum, not a height**, so a cluster with four collections renders at its natural height with no scrollbar and looks exactly as it did; only the long tail caps and scrolls, and only the long tail was the problem. **`initialRect` is load-bearing**: the server has no element to measure, and without it the virtualizer reports a viewport of zero and renders no rows, which is how a virtualized table silently stops being server-rendered — the failure mode the TanStack DB spike had just demonstrated. Proven by a `renderToString` test asserting the first row is in the HTML and the last is not, because the e2e SSR test cannot see it (the e2e cluster has no collected rows). Two things this does **not** fix, deliberately: the payload is still unbounded, since virtualizing is a render-cost fix and a cluster with 20k recommendations still ships 20k rows of JSON — that wants a limit or a cursor on the contract, which no read currently takes; and the audit trail is left alone because the api already caps it at fifty. One test-harness consequence: jsdom performs no layout and reports `offsetHeight`/`offsetWidth` as 0, which are the exact two properties the virtualizer measures, so `vitest.setup.ts` now shims them at a plausible scale (600px container, 40px rows) — left at zero every table test fails on markup that is correct in a browser | Locked |
| D33 | **Tables are headless; the sort order is a decision, not the api's leftovers** | Aug 2026. The recommendations, per-collection and audit tables were `<table>` markup with the rows mapped inline: no sorting, no filtering, a header row kept in step with the body's by hand, and a 379-line route that was mostly cells. Fifty recommendations arrived in whatever order the api returned them, which is the one order nobody wants. TanStack Table for the logic, the **same shadcn primitives** for the markup, one `DataTable` for all three — so this is not a visual rewrite, and the column defs carry what the markup could not say: how to read a value, how to draw it, and how to sort it, in one object. **v9, not the v8 that shadcn's data-table page documents**: 9.0.0 is the `latest` tag, the repo's standing rule is latest stable (§2.6), and v9's opt-in feature registry is a real gain here — what a table can do is settled statically, so the grouping, pagination and row selection none of these three use are not in the bundle.   predates the migration. `@OrgRoles("owner")` inherits that, and adds an api
  call to fetch a role `resolveMembership` already returns beside the org id the
  handler actually needs — which a decorator cannot hand it. What the package
  gets genuinely right is the one thing worth taking: its `AuthGuard` resolves
  the session **once** per request and attaches it, where the api resolved it up
  to three times. Taken without the mount (#77): `requireSession` memoizes the
  resolution per request in `auth/session.ts`, and `session.cookieCache` keeps
  the common case off postgres entirely, re-armed on ordinary responses by the
  `onSend` hook in `main.ts`.
- **TanStack DB** (`@tanstack/react-db` 0.1.95 / `db` 0.6.17 /
  `query-db-collection` 1.2.1) — spiked Aug 2026 (#42), **not adopted**. It fails
  the gate the issue set for it, and fails it harder than expected: a collection
  does not merely start empty on the server, `useLiveQuery` **cannot be
  server-rendered at all**. It calls `useSyncExternalStore` with no
  `getServerSnapshot`, which React requires on the server — no hook in the package
  passes one, and `useLiveSuspenseQuery` delegates to `useLiveQuery`, so it
  inherits the gap.

  Measured on the real app with one collection over `getCollections`, and the cost
  is not scoped to the panel that used it. React's recoverable-error path reverts
  the **whole `/app` shell** to client rendering, so the server HTML went from
  36,660 bytes to 17,127 and `Sign out`, `Collections` and `Policy` all
  disappeared from it. The dashboard still worked — the dehydrated query cache is
  independent of the collection, and the collection reads it on the client with
  **zero** refetches, which is the one part that worked exactly as hoped — but
  every panel was drawn after hydration instead of arriving drawn. The only symptom
  was one line per render in the web server's log: `Error in
  renderToReadableStream: Missing getServerSnapshot`. A warning is a defect (D20).

  Two findings outlive the "no". **The gate named in the issue could not detect
  this** — `renders from what the server sent` runs with JavaScript on, so it
  cannot tell server output from a client re-render off the hydrated cache, and it
  stayed green throughout. A test that reads the raw `/app` response was added
  beside it. And **the module-level collection the docs describe is unusable here
  regardless**: `queryClient` is required config, `createAppQueryClient` is
  per-request on the server, so a module-level collection would serve one tenant's
  rows into the next tenant's render. A `WeakMap` keyed by client is a workaround,
  not a shape the library expects.

  Revisit when the React adapter server-renders, and preferably alongside #22:
  a collection with an SSE sync source updates every live query touching it with
  no invalidation, which is a real argument the read-side rewrite is not. The rest
  of the issue's own case was already thin by its own admission — on-demand sync
  needs filter params no contract in `packages/contracts` takes, differential
  dataflow is irrelevant at a cluster's row counts, and `roi`, `latencySeries` and
  `policy` are not collections. The hand-rolled join it would delete is now six
  lines in `toCollectionRows`, with tests.
- **`nestjs-trpc`** — considered Aug 2026, **staying on `@orpc/nest`**. tRPC infers
  the client's types from the server's implementation, which would replace
  `packages/contracts` — a shared artifact both sides are checked against — with
  a dependency on the api's internals. It would also cost the REST surface: the
  contract carries real routes and generates the OpenAPI document that
  `ingress.api.*` exists to expose, and `/trpc/listClusters?input=…` is not an
  api anyone wants to consume. No pain reported with oRPC, and subscriptions are
  not the deciding factor either — the passthrough already streams (§14.5), so
  #22 does not need a different RPC layer.
- **Agent mode** — phase 2. Interface designed for it from day one.
